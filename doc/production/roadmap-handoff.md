## 首要风险

| 优先级 | 风险 | 影响 | 处理门槛 |
| --- | --- | --- | --- |
| P0 | 切片未完整人工游玩 | 自动测试无法发现导航、焦点、输入和理解问题。 | 扩展内容前完成测试矩阵。 |
| P0 | Dialogue Manager 未接入 | `.dialogue` 与硬编码对白可能继续漂移，扩写成本翻倍。 | Day 3 对白制作前完成插件适配。 |
| P0 | 缺 Windows 导出模板 | 无法验证最终包、资源包含和用户目录。 | 对外测试前取得完全匹配模板并导出。 |
| P1 | `MainController` 职责过多 | 新事件继续硬编码会快速失控。 | 插件接入时拆出事件呈现/导演职责。 |
| P1 | 后续房间正式美术和音频缺失 | 第一室已验证图块/机关/角色管线，但走廊与后三室仍是原型图形。 | 沿用第一室图集规范逐室迁移，并在盲测后补最小音频集。 |
| P1 | Day 3–7 仅场景草案 | ID、具体对白、地图尺寸和资源预算尚未落数据。 | 每阶段先做内容表和状态契约评审。 |
| P2 | 导出地点白名单固定 | 新地图存档会被拒绝。 | 每新增地图同步存档校验和测试。 |

## 推荐实施顺序

### 阶段 0：接手复现（1–2 天）

1. 阅读 `AGENTS.md`、当前实现、架构和剧情圣经。
2. 在接手机器记录 Godot/.NET 实际路径并复跑 71 项测试与场景冒烟。
3. 用 Godot 编辑器从头完成一次主路径，记录所有与文档不一致处。
4. 不在这个阶段升级版本、改剧情或扩地图。

完成条件：接手者能解释唯一 `GameState`、事件原子性、当前对白替代层和 Day 1–2 状态链。

### 阶段 1：垂直切片验收（原计划第 3–6 周收尾）

1. 覆盖三种共同活动、三种异象选择、重试/撤退、存读档和连续睡眠。
2. 覆盖键鼠、Xbox、720p/1080p、字号和故事模式。
3. 修复软锁、焦点、提示和手册问题；不增加新系统。
4. 邀请 2–3 名熟人盲测，要求能指出两项因果反馈。

完成条件：测试矩阵通过，盲测者无需讲解完成切片。失败时继续迭代切片，不进入阶段 3。

### 阶段 2：Dialogue Manager v3.10.4 接入

1. 将匹配版本放入 `addons/dialogue_manager/`，记录版本/tag 来源，不升级到 3.10.5。
2. 保持 `Narrative` Autoload 和 Core 状态不变，用插件运行现有八个 `.dialogue`。
3. 将当前逐条 `NarrativeBridge.Execute` 迁移为 `eventId + outcomeId` 对应的 C# 预定义 mutation，或等价的缓冲后一次提交，确保取消、重进和载入幂等。
4. 删除 `MainController` 中重复的对白文本和分支编排，保留应用导航与事件入口。
5. 增加插件加载、反射签名和八事件回归验收。

完成条件：游戏内显示文本来自 `.dialogue`，硬编码副本不存在，71 项测试及 Godot 冒烟仍通过。

### 阶段 3：Windows 原型包

1. 环境具备完全匹配的 4.6.3 Mono 导出模板后执行 Release 导出。
2. 验证离线启动、资源、本地化、存档、中文/空格路径和 ZIP 解压运行。
3. 记录集显 60 FPS 和约 2 秒切图指标。

完成条件：得到可在另一台 Windows x64 机器运行的免安装 ZIP。模板缺失时保持阻断状态，不伪造完成。

### 阶段 4：完整小镇与人物（原计划第 7–11 周）

1. 补旧宅/住宅巷、车站/商店街、学校/河岸、山林/废线及必要室内。
2. 将何医生、温老师、罗记者、彭师傅加入角色 catalog、日程、关系、立绘和个人事件。
3. 完成三名伙伴的中期关系事件、居民支援、经济、等级和最小装备集。
4. 先实现 Day 3 的“居民调查 + 第一节点”，验收后再实现 Day 4。

完成条件：8 名核心 NPC 都有可理解作息和至少一个事件；玩家未做 Day 1 活动也能补齐核心事实。

### 阶段 5：双路线（原计划第 12–15 周）

1. 做完四级暴露的可见征兆和路线锁定说明。
2. 谨慎线实现巡逻观察、潜入、被发现战斗和节点破坏。
3. 救援线实现绑架、仅用于拖延救援的伪证、信赖召集、匿名补给、策反、取证和救人。
4. 验证证据完整/不完整、有人/无人同行、撤退和低资源路径。

完成条件：绑架确实可通过谨慎选择避免；两线都能继续终战；社会与资源回报差异清晰但无道德优劣标签。

### 阶段 6：终战与尾声（原计划第 16–18 周）

1. 实现共鸣保护、历史判断、怀表节点、居民危机和最终稳定阶段。
2. 接入三项关键事实、节点、证据和高信赖居民的结局判定。
3. 实现领袖劝停/顽抗但必须担责，以及恋爱、友情、倒戈者和居民支援尾声。
4. 为每一档结局提供低资源但可完成的路径。

完成条件：三档结局可稳定复现，步骤失误、战败或关系不足不软锁。

### 阶段 7：回归与缓冲（原计划第 19–24 周）

只修复完整回归、性能、输入、无障碍、剧情软锁、资产一致性和兼容问题。21–24 周缓冲不新增系统或扩张内容范围。

## 每个内容日的交付包

新增 Day 3–7 内容时，每个内容日必须同时交付：

- 场景和事件清单，含固定/草案标识；
- 稳定 ID 表和状态结果；
- JSON、`.dialogue` 和本地化；
- 必要地图、anchor、角色和资产 provenance；
- Core/内容测试与场景冒烟；
- 主路径、低关系、错过时段、失败/撤退和读档人工记录；
- 当前实现、剧情流程和本路线图状态更新。

不要一次提交“整日对白”再补规则。先纵向完成一条可玩的事件链，再扩支线。

## 固定决策与可调整项

### 固定

- Godot/Dialogue Manager 版本、Windows 离线范围和唯一状态架构。
- 主题、主角弧线、主角与林晓雨现实中此前未见且梦中初遇、古老存在非语言且无善恶。
- 居民无内鬼、普通组织成员不知真实计划。
- 舆论仅用于阻止救援，领袖创伤不免除责任。
- Day 5 根据身份确认分线，双路线都可完成。
- 三名伙伴在终战分别承担共鸣、知识和信物职责。
- 三档结局和低资源不软锁原则。

### 可调整草案

- Day 3–7 具体事件拆分、对白、场景时段和非核心地点。
- 古老存在的民间称呼、领袖及普通成员姓名。
- 每场战斗的数值、敌人组合和视觉表现。
- 关系事件的具体活动、礼物名称和部分尾声文本。
- 在 20–25 个事件组目标内的合并与拆分。

调整草案时必须更新剧情流程并检查是否改变资产、地图、测试和存档预算。

## 交接完成定义

新接手者在无原作者口头说明下，应能：

1. 用正确 Godot 版本运行工程，复现测试和冒烟。
2. 从 `GameSession` 追踪一次选择如何写入、保存并在手册反馈。
3. 说明当前 C# 对白和未来 Dialogue Manager 的边界。
4. 讲清组织动机、古老存在、三伙伴职责、两条路线和三档结局。
5. 按内容制作清单新增一个不软锁、可本地化、可验证的事件。
6. 从本路线图选择下一项工作，并准确区分“已实现、计划、固定约束、可调整草案”。

如果任一项只能依赖个人记忆或聊天记录完成，应先补文档再继续开发。
